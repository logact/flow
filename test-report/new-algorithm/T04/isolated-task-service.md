# T04 isolated task service evidence

- Added `/api/new-algorithm/task` backed by `getNewAlgorithmDb()` and `lib/new-algorithm-task-service.ts`. The legacy `/api/task`, `lib/db.ts`, and `flow.db` were not opened or changed.
- GET reuses the single live instance or issues an available unintroduced double-zero ENCODE, then an eligible target-axis choice task. Candidate order is due timestamp, word ID, R before P. Current scope deliberately returns `EMPTY/materials_unavailable` when the needed stage is not yet supported or has no ready material; it never downgrades the stage.
- Issued snapshots freeze the exact `capacity_reservation_id`, public payload, and target context. Material usage is claimed when issued. Public payload serialization recursively strips answer-key-shaped fields; private choice keys stay in `materials.answer_key`.
- POST accepts connection confirmation or a choice `selected_index`. Choice material currently requires a private integer key named `correct_index`, `correctIndex`, `answer_index`, or `answerIndex`; unsupported answer key shapes fail closed. The first accepted response is persisted in the same transaction as T02 settlement. Exact repeats replay the prior outcome; different repeats return `INSTANCE_CONFLICT` (HTTP 409).
- Daily reservation capacity, configured local training window, and shared cooldown gates are checked before issue. EMPTY reports `cooldown_wait` only when a ready, reserved candidate is waiting; unsupported/missing material does not hide another candidate's cooldown. SQLite's one-live-instance partial unique index plus transactional selection/insert prevents a second live issue.
- Tests: `npx jest --runInBand test/new-algorithm-task-service.jest.test.cjs` — PASS, 1 suite / 7 tests. Coverage: live issue reuse, connection dual-axis write and one-time capacity consumption, correct and incorrect choice update only the selected axis, answer-key redaction, duplicate replay/conflict, cooldown/window/material EMPTY cases, and HTTP GET/POST against a fresh temporary prototype DB.
