# Loop6 实施计划

## Loop5 遗留问题

以下两项来自 [Loop5 实施计划](../loop5/loop5.plan.md) 完成度核查，当前实现尚未满足 Loop5 的明确要求，纳入 Loop6 继续处理。

### 场景 1：候选解析的跨进程并发去重与幂等

#### 来源与现状

- 来源：Loop5 场景三，要求显式触发、并发去重、幂等操作标识和可恢复状态。
- 当前候选解析接口用进程内 `Set` 按材料 ID 去重，并在调用 provider 前持久化 `processing` 状态。
- 进程内 `Set` 无法协调多个服务进程；候选解析请求没有持久化操作 ID。因此多实例或跨进程并发重试仍可能重复调用消歧/翻译 provider。重启后可由用户显式重新提交处理中候选恢复，但不代表后台任务自动续跑。

#### 目标

对同一材料分析版本及候选解析操作建立可持久化、跨进程有效的去重与幂等语义。重试能够读取或继续已有操作结果，不产生重复的并发 provider 调用；进程中断后仍可查询状态并显式恢复未完成候选。

#### 实施计划

**Domain**

- 明确候选解析操作的身份、状态、分析版本关联及可恢复状态转换；保留逐候选成功/失败结果。

**Service**

- 以 SQLite 等持久化协调机制实现跨进程原子认领/锁定，并对重复操作 ID 返回已有操作状态或结果。
- 在调用消歧和翻译 provider 前完成原子认领；处理租约过期或进程中断后可安全恢复，避免将持久化 `processing` 误当成仍有活跃 worker。
- 继续支持逐候选持久化、失败项重试和部分成功；操作需绑定材料及分析版本，拒绝过期或越权请求。

**UI**

- 展示操作处理中、可恢复、成功及失败状态；发生重复提交时呈现已有操作状态，不将其显示为无法恢复的错误。

#### 验收

- 两个独立进程同时提交同一解析操作时，provider 对每个候选至多执行一次，后续请求读取同一操作状态/结果。
- 同一操作 ID 重试不会重复创建解析结果或知识点；不同候选仍可分别成功、失败和重试。
- 在 provider 调用期间终止进程，重启后可查询持久化状态并显式恢复未完成项；已完成项不会再次调用 provider。
- 覆盖 SQLite 多连接/多进程场景的自动化测试，并验证 memory 后端的约定行为。

### 场景 2：分析完成后独立触发发音补全

#### 来源与现状

- 来源：Loop5 场景四，要求分析主体保存完成后独立触发发音查询，发音失败不影响分析结果。
- 当前发音接口能单独查询并持久化 `processing`、`complete`、`failed` 状态；知识点详情页提供手动查询/重试。
- 当前未发现知识点/材料分析完成后自动触发发音补全的调用路径，因此只具备手动补齐，尚未满足“分析完成后独立触发”。

#### 目标

材料主体分析及候选解析结果持久化完成后，发音查询作为独立、非阻塞的增强流程自动排队或触发。查询失败或无匹配时保留已完成的分析和知识点，状态可查询，用户仍可单项重试。

#### 实施计划

**Domain**

- 保持发音数据可缺省；发音补全状态与材料分析/知识点确认状态分离。
- 明确待补全知识点的筛选条件，排除不支持发音的知识点及已有完整发音项。

**Service**

- 在主要分析结果成功持久化后独立触发发音补全，不等待词典响应再返回分析结果。
- 对发音补全执行去重/限流并持久化进度与失败状态；进程中断后可查询并恢复待处理项。
- 保留单项重试；失败不得回滚分析、候选解析或已保存的发音数据。

**UI**

- 展示待查询、查询中、完成及失败状态；失败项保留单独重试入口。
- 发音补全中的状态不将材料分析标记为处理中或失败。

#### 验收

- 主体分析保存完成后发音补全会自动独立启动；慢速或失败的词典请求不延迟主体分析完成响应。
- 发音接口不可用或无匹配时，分析和知识点仍保持成功；失败状态可在刷新/重启后查询并可单项重试。
- 并发、重复触发和重启恢复不会造成重复查询或清除已有发音。
- 覆盖成功、无匹配、超时/异常、重复触发及主体分析不受影响的自动化测试。
