# 材料分析拆分计划

## 目标

将材料分析拆分为可独立完成的本地筛选、后台 LLM 处理与可选发音补全，避免词义消歧、释义翻译或词典查询拖住整个分析请求，并让页面展示真实进度。

## 已确认的处理边界

- 文本提取后，分句、分词、词形归并、词表过滤及本地词义库查找均为确定性本地步骤，不依赖 LLM。
- 词义库只有一个候选义项时可直接归属；存在多个候选义项时，才需要 LLM 根据上下文消歧。
- 中文释义翻译需要 LLM。
- 发音查询使用外部词典 API，不是 LLM，属于可选增强，不应阻塞主要分析结果。

## 实施场景

### 场景一：文本提取与本地候选生成

**Domain**：明确候选词项、已确定义项、待消歧义项及被过滤项的数据形态；不把未消歧多义词标成最终知识点。

**Service**：提取并保存文本后，执行本地分词、词形归并、词表筛选及词义库匹配；单义词直接生成已确定归属，多义词保存候选及语境供后续任务处理。

**UI**：材料上传后显示“待分析”或“候选已生成”等准确状态；用户显式启动分析，避免把空 pending 记录显示成正在运行。

### 场景二：后台 LLM 消歧与释义翻译

**Domain**：定义 LLM 处理中的状态、部分结果、失败原因及完成状态转换。

**Service**：将多义词消歧和释义翻译提交到持久化后台任务；任务应支持重启恢复、幂等执行、失败重试及阶段耗时/进度记录。生成并保存阶段结果，不让前端分析请求一直等待 LLM 完成。

**UI**：展示“候选已生成、正在消歧、正在补充释义、已完成、部分失败”等状态；提供失败原因和恢复操作。只有分析任务真正运行时才显示“分析中”。

### 场景三：独立发音补全

**Domain**：发音数据可缺省或稍后补齐，不影响分析已完成状态。

**Service**：分析主体完成后异步查询词典发音，按需限流并去重；单条失败可独立重试，不回滚知识点结果；记录阶段耗时与失败情况。

**UI**：发音尚未补齐时显示无发音/加载状态；失败时允许重试，不将材料分析显示为失败或 pending。

## 执行顺序

1. 定义候选与最终知识点状态，以及分析和发音任务的状态转换。
2. 实现本地筛选结果落库，验证其不触发 LLM/词典请求。
3. 加入持久化后台任务机制，接入多义消歧和释义翻译，补充进度、耗时、重试和重启恢复。
4. 将发音查询移出主要分析完成路径，支持独立补齐和重试。
5. 更新列表与详情页状态展示及显式启动/恢复入口。

## 补充方案：未解析知识点的可见性与按需解析

### 产品决策

- 不要求新增后台定时/常驻 worker，也不要求材料导入后自动调用 LLM。解析由用户动作触发，避免用户未打算学习的候选词消耗模型调用。
- 材料详情应能看到本地筛选后仍未形成可用知识点的候选（例如多义待消歧、缺少中文释义、上次解析失败），并显示数量、候选词及其语境/原因。需区分“待解析”与“未匹配/被过滤”：词表过滤项不是待解析知识点，不应提供解析按钮。
- 提供材料级“解析待处理知识点”操作；允许处理中状态和结果逐项/分批更新，失败项可重试。已解析项不重复请求，操作应幂等并避免并发重复调用。
- 在目标创建/编辑界面，用户选中材料后看到其已解析知识点以及未解析候选。用户可先挑选候选；提交创建目标/生成任务时，仅对本次选中的待解析候选同步触发解析，成功后再将可用知识点纳入目标并生成任务。未选中的候选保持待处理。
- 解析是显式动作，接口仍由前端请求启动；无需后台定时解析。请求较慢时界面提供处理中反馈和重试入口，避免重复提交。

### 领域与接口边界

- 将“候选解析状态”与材料整体分析状态分开表达。材料完成本地候选生成后即可展示候选；解析状态至少覆盖待解析、处理中、已解析、失败。材料整体的提取/本地分析失败不能和单个候选的 LLM 失败混为一谈。
- 现有已解析知识点保持可学习；未解析候选暂不创建最终知识点、目标选择记录或学习任务，防止把未消歧内容误当确定知识点。
- 材料级入口处理该材料全部可解析的待处理候选；目标提交入口只处理所选候选。服务端需校验候选归属材料、状态和用户权限，并对重复请求去重。
- 目标提交按“解析所选候选 → 返回解析结果/失败项 → 用成功知识点创建或更新目标选择并生成任务”执行。若部分失败，应明确告知哪些知识点已成功、哪些未解析；不静默丢弃失败项，也不将失败项生成任务。重复提交不得重复创建目标或任务。
- 目标页初次加载及选择过程只读取状态，不自动触发解析；只有材料详情按钮或用户明确提交目标时才解析。对于可能超时的批量操作，应返回可查询的 operation/status 标识，页面轮询同一操作，不能因刷新重发一组 LLM 请求。

### UI 展示与操作

- 材料详情在已解析知识点之外新增“待解析候选”区域，展示待解析/处理中/失败数及候选词、语境和失败提示；提供“解析待处理知识点”及失败项“重试”。无候选时不显示空操作区。
- 目标材料/知识点选择区将已解析知识点与待解析候选分组，候选可选中但标明“需解析后加入”。提交按钮文案应说明将解析所选候选；处理中禁用重复提交并展示进度。解析完成后刷新选择列表，保留用户当前选择意图。
- 对部分成功结果给出明确反馈，提供失败候选重试；当没有可用解析结果时，不创建空目标/空任务，并保留用户填写的目标草稿。

### 建议实施顺序与验收

1. 盘点当前分析模型和页面是否已保存多义待处理候选；补齐持久化候选及逐项解析状态，确保重启后仍可见。
2. 为材料详情提供候选列表、显式批量解析及单项重试 API/UI。
3. 扩展目标选择数据契约，使未解析候选可被暂存选择；在目标提交服务端仅解析选中项，成功项进入目标，失败项保留待重试状态。
4. 对部分失败、超时/刷新、并发提交和幂等创建定义结果反馈与恢复行为。
5. 验收：进入详情/目标页不会调用 LLM；材料详情能看到未解析候选；材料入口能手动解析；目标提交只解析被选项；失败候选不生成任务且可重试；重复点击/刷新不会重复解析或创建任务；未选择候选不产生模型调用。

### 与既有实现的衔接

- 继续沿用材料详情 GET 只读、显式 POST 启动分析的约定（见 `docs/loop/loop3/material-detail-manual-analysis.decision.md`）；此方案增加的是本地候选之后的按需解析，不应把打开页面变成自动分析。
- 复用材料和分析状态现有文案约定，但候选级失败应在候选列表内表达，不把整份材料错误标记为失败（见 `docs/loop/loop3/material-analysis-status-copy.decision.md`）。
- 需要先核对当前 `MaterialAnalysis` 是否实际持久化了未解析多义候选；如当前流程只保存最终分析结果，则需先扩展领域模型、SQLite 序列化/迁移及 API DTO，不能只在 UI 临时推导。

## 验收要点

- 本地候选筛选可以在没有 LLM 配置时完成，并正确标出单义、多义候选和排除项。
- 多义词最终归属在消歧前不被误报为已完成；单义词不等待 LLM 消歧。
- 分析 API 不因后台 LLM 或发音查询持续数分钟而保持请求 pending；任务状态可在服务重启后恢复。
- LLM 或词典部分失败只影响对应补充阶段，错误可见且能重试；发音失败不影响分析完成。
- 页面状态能区分待启动、后台处理中、部分完成、失败和完成。

## 待实施时确认

- 当前运行时使用内存仓储，持久化后台队列需要确定实际存储和 worker 生命周期；进程内 `Set` 不能满足重启恢复。
- 确认分析结果采用分阶段更新还是先保存候选、再替换/补齐最终知识点，并处理材料/分析版本一致性。
