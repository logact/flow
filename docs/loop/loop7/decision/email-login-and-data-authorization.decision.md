# 邮箱登录与业务数据鉴权决策

## 决策

- 采用邮箱验证码登录；验证码邮件由 QQ 邮箱 SMTP 服务发送。
- 使用 `userId` 作为账号身份标识。登录会话在服务端关联到 `userId`，再由服务端解析该账号对应的 `learnerId`。
- 业务数据以 `learnerId` 作为学习数据范围。接口不得把客户端提交的 `userId` 或 `learnerId` 当作授权依据；按资源 ID 访问时必须验证资源属于当前会话对应的学习者。
- 当前所有业务学习数据均为用户私有数据，不设匿名业务接口或共享数据例外。验证码登录相关接口允许匿名访问，并需限制发送及验证频率。
- 所有现有学习数据 API 均纳入鉴权改造，覆盖 learner、plan、assessments、tasks、materials、goals、knowledge 及其子路由。

## 实施边界

- 调整 repository / 数据访问能力，使学习数据查询与写入能够限定到当前 `learnerId`。
- 建立用户账号与学习者的持久化关联，并设计现有演示数据的归属方式，避免与新用户数据混用。
- 登录态由服务端会话管理；浏览器仅携带安全 Cookie，不自行决定访问范围。
- 邮箱验证码的有效期、一次性消费、重发间隔、尝试次数、会话过期与退出失效属于实施计划需要细化的安全行为。

## 调查依据

- 当前 repository 契约只有无参数的 `load()` 和以全状态为输入的 `save()`，不能按用户隔离。
- SQLite 虽有若干 `learner_id` 关系列，当前仓储仍将状态作为全量快照读写；现有结构不足以直接提供多用户鉴权。
