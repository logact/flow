# Loop4 实施计划

## 决策覆盖与冲突检查

本计划覆盖 [Loop4 记录预处理决策](loop4-review.decision.md) 的四条决策。四条决策可归并为三个实施场景：界面反馈、材料分析启动与状态、材料分析可靠性。发音反馈与材料分析的发音查询相互关联：词典音频不可用不得阻断分析，学习页播放问题仍需独立提供诊断和恢复信息。当前未发现其他决策冲突。

## 场景 1：界面动效与发音播放反馈

### 纳入决策

- 第 1 条：只对确实表示进行中状态的控件使用克制的加载反馈；状态结束后停止，并尊重减少动态效果偏好。
- 第 4 条：区分无音频、播放中与播放失败，失败时提供可诊断的来源或重试信息；音频不可用不得导致分析失败。

### 实施计划

**Domain**

- 不涉及领域模型变更。

**Service**

- 核对材料分析保存的音频 URL 来源与有效性；词典查询失败继续作为非阻断增强处理。
- 保持播放使用已保存的音频 URL，不在用户点击播放时隐式发起词典查询。

**UI**

- 复现并定位持续闪烁来源，确认是否由轮询、状态更新或 CSS 动画导致。
- 仅在真实进行中状态显示克制动效；状态完成或失败时停止，并支持 `prefers-reduced-motion`。
- 发音控件明确呈现无音频、播放中、播放失败状态；失败时提供重试及可用的音频来源/错误信息。

### 验收

- 静止内容与可点击控件不持续闪烁；减少动态效果开启时不出现非必要动效。
- 无音频、播放成功、媒体错误及浏览器拒绝播放时，控件状态清楚且可恢复。
- 词典音频不可用不会使材料分析失败。

### 实施记录

- 已完成 `TaskCard` 发音反馈：媒体加载错误与浏览器拒绝播放会显示不同的恢复提示；有音频时按钮可再次点击重试，保留来源链接；全局减少动态效果样式已覆盖现有加载动画。
- 变更：`components/learning/TaskCard.tsx`。

## 场景 2：材料分析显式启动与状态呈现

### 纳入决策

- 第 2 条：分析由用户显式启动；进入详情、刷新页面和上传完成均不自动分析，入口文案须清楚。

### 实施计划

**Domain**

- 检查当前状态语义能否区分未启动、处理中、完成与失败；仅在确有必要时调整状态模型。

**Service**

- 保持详情 GET 只读，分析 POST 由用户操作显式调用。
- 避免上传时创建会被误解为正在运行的空 `pending` 记录；若需保留记录，提供明确的未启动语义并确保列表、详情按同一语义解释。

**UI**

- 检查材料列表与详情页的分析入口可发现性和文案，明确说明分析需要用户主动开始。
- 未启动、处理中、完成、失败及超时可恢复状态在列表和详情中表达一致；处理中状态才轮询并显示进行中反馈。
- 进入或刷新详情不触发分析请求；可恢复状态提供明确的恢复/重试操作。

### 验收

- 上传材料后不自动分析；打开或刷新详情不调用分析 POST。
- 新上传材料能直接找到显式启动入口，不会被误显示为正在分析。
- 列表和详情的状态语义一致，恢复操作由用户明确触发。

## 场景 3：分析进度、超时与失败收敛

### 纳入决策

- 第 3 条：保留可恢复的 pending；向用户呈现失败原因与最后进展；分析需收敛到明确超时/失败，且重试不应永久等待超时窗口。

### 实施计划

**Domain**

- 补充 pending 阶段和最后进展时间语义；失败状态继续携带原因。

**Service**

- 对文本准备、候选/词义处理、释义补全、发音增强、结果保存记录可观察进展；对主分析链设置端到端时间界限，超时落盘为 failed。发音增强失败继续非阻断。
- 过期 pending 可以显式恢复；同进程正在执行的任务仍返回冲突并说明稍后重试。

**UI**

- 在列表和详情呈现当前阶段、最近进展时间；失败显示原因和明确重试入口。
- pending 超过合理时间显示可恢复提示；处理中轮询且只在真实处理中反馈加载状态。

### 验收

- 服务异常或分析超时后，记录最终为 failed 并保留可读原因；刷新页面可看到结果。
- 分析进展可从持久化记录及日志追踪；词典服务异常不阻断分析完成。
- 超时 pending 可由用户立即恢复，活跃请求不会被并发重复执行。

### 实施记录
