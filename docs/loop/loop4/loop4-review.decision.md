# Loop4 记录预处理决策

## 第 1 条：界面元素不停闪烁

- 调查结论：记录引用的 `image-11.png` 未随 `new.record.md` 提交，当前无法从截图确认具体控件；需要在实施时复现并定位动画来源，检查是否由 pending 轮询、状态更新或 CSS 动画造成持续闪烁。
- 决策：只有确实表示进行中状态的控件可使用克制的加载反馈；静止内容和可点击控件不得持续闪烁。动效应在状态完成/失败时停止，并尊重减少动态效果偏好。
- 实施范围：Domain 不涉及；Service 不涉及；UI 排查动画来源并修复。

## 第 2 条：材料分析需要用户选择后再分析

- 调查结论：材料详情 GET 只读，详情页不会自动触发分析 POST；上传文件 POST 也只保存原文，没有调用分析用例。但上传接口在保存材料时同时创建了 `status: 'pending'` 的空分析记录。详情页将所有 pending 一律显示为“分析中”，并每 5 秒轮询；未超时前按钮显示“恢复并重试分析”但禁用。于是用户上传后首次进入详情就会看到“正在分析”，即使实际上没有分析任务在运行。列表页同样把该状态显示为“分析中”并禁用按钮。详情页的“开始分析”分支仅在分析记录为 `null` 时出现；普通上传流程总会创建记录，所以该入口对新上传材料通常不可达（仅旧数据或缺失分析记录时可见）。相关代码：`app/api/materials/route.ts`、`app/materials/[id]/page.tsx`、`app/materials/page.tsx`。
- 决策：保留显式启动分析，不因上传完成、进入详情或刷新页面自动分析。入口文案应清楚表达用户需要主动选择启动。
- 实施范围：Domain 不涉及；Service 保持详情 GET 只读、POST 显式启动；UI 检查列表和详情入口的可发现性与文案。

## 第 3 条：材料分析一直 pending

- 调查结论：分析 POST 先落盘 `pending`，完成后保存 `analyzed`；业务失败或异常时尝试保存 `failed`。进程在 pending 写入后退出，或失败状态落盘失败，记录会留在 pending。
- `logs/app.log` 没有截图中 `day-bamford-2002-top-ten-principles.pdf` 的文件名或对应记录 ID，不能据此还原该材料的请求过程。日志中有两次 37,051 字符的 `nation-2007-four-strands.pdf` 分析，分别约 54.9 秒和 54.4 秒完成，且保存了 352 个知识点；这只能说明相近的大 PDF 曾完成，不能证明截图中的记录也完成过。
- 后续用户重新分析了 `nation-2007-four-strands.pdf`。本次运行 ID 为 `3a01ceb2-be9c-4130-9ee1-aba3859c284f`，日志从 2026-11-16 19:49:02.130 到 19:52:18.173（Asia/Shanghai），总计 196.043 秒；输入文本 37,051 字符，最终保存 352 个知识点、1,346 处词项。19:49:02.130 的开始日志与文本提取完成日志同毫秒，提取不是主要耗时。
- 分阶段证据：`logs/ai.log` 中词义消歧请求从 19:49:02.142 持续到 19:49:56.091，约 54 秒，共 31 个消歧请求；其中 `logs/app.log` 明确记录 1 个 AI 批次失败并回退占位义项。随后 AI 日志有 337 组底层 LLM 请求发送/成功记录，覆盖 19:49:56 至 19:51:15，约 79 秒，成功请求平均约 0.73 秒（有并发，不能把单次耗时简单相加）。最后一条 AI 日志至分析保存日志之间仍有约 63 秒（19:51:15.098 至 19:52:18.173）。
- 代码 `lib/application/material-import.ts` 表明词义分配后还会逐批、每批最多 4 个知识点调用 `pronunciationLookup`，之后才写入分析结果；单次词典请求超时设为 4 秒。该阶段没有耗时日志，故最后约 63 秒很可能主要花在词典发音查询（352 个条目最多形成 88 批），但目前只能作为代码与时间间隔支持的推断，无法从现有日志证实每批实际请求数量/耗时。翻译与发音查询也都没有阶段进度日志。
- 管线拆分调查：上传接口 `app/api/materials/route.ts` 已经先提取文本并保存 `material.extractedText`，但此步骤仍在上传 POST 内同步执行；候选词处理要等显式分析 POST 才执行。`extractMaterialTerms`（`lib/domain/functions.ts`）仅做分句、分词、词形归并并保留语境，是确定性本地处理。其后 `resolveSenseAssignments` 先调用本地词表过滤器及本地词义库：词表未保留或词义库未收录的词直接排除，只有一个候选义项的词直接归属；这几步不调用 LLM。多个候选义项时才采样出现语境并调用 LLM 消歧，所以“筛选词/候选知识点”可独立于后续 LLM；但多义词的最终义项归属依赖消歧，不能在 LLM 前当作已定稿。
- 分析完成后的 `analyzeMaterial` 只是把义项归属组装成知识点结构；随后当前实现会等待释义翻译（LLM）和发音查询（`dictionaryapi.dev` 外部词典，不是 LLM），二者都在同一个分析 POST 中、保存 analyzed 结果之前顺序分批执行。翻译缓存按 senseId/definition 复用结果；发音查询对词条逐项请求，每批并发 4 个，失败不阻断但仍需等请求完成或 4 秒超时。当前没有后台任务队列，所谓异步调用只是服务端 `await` Promise，并不代表 API 已返回、任务在后台运行。
- 可行拆分方向：文本提取后可同步完成本地分词、词表/词义库筛选并保存候选/基础知识点；把多义词消歧与释义翻译放到可持久化后台任务，前端显示阶段进度并在任务完成后补齐/更新知识点。发音查询与主要知识点分析相互独立，且是非 LLM 的可选增强，可在分析完成后单独后台填充，失败可重试而不影响 analyzed 状态。需要另行设计任务持久化/重启恢复、候选和最终状态语义、重复执行幂等、结果部分完成时 UI 展示，以及开发环境是否有常驻 worker；当前进程内 `Set` 不足以承担持久后台队列。
- 当前 `.flow/flow.sqlite` 中确有一条超过 2 分钟的 `pending` 分析，但其材料是 `nation-2007-four-strands.pdf`，创建于 `2026-11-16T02:34:18Z`，记录 ID 与日志中的两次成功运行都不同。`logs/app.log` 没有这条记录 ID。它和截图中的 day-bamford 文件名也不一致，因此不能把数据库里的 pending 直接认作截图那条材料。
- 代码上，详情页每 5 秒轮询，创建时间超过 2 分钟后标记超时并展示恢复按钮；API 的两分钟仅是允许重试的门槛，不是分析总时限。单次请求同步等待词义消歧、释义翻译及发音查询；LLM 单次调用默认最多 60 秒、可重试 3 次，但整个分析没有总时限。当前进程内 `analyzing` 集合可阻止同一进程重复请求；如果仍在分析，重试会返回 409。进程重启后该集合丢失，而 pending 是持久化的，所以会出现截图中的可恢复状态。
- 结论：本地代码和当前数据库复现了“过期 pending”状态，但截图所指的 day-bamford 材料仍无法通过日志定位。对齐到的 nation-2007 本次成功运行耗时 196 秒，超出页面 2 分钟提示门槛约 76 秒；至少约 54 秒用于消歧、约 79 秒用于后续 LLM 请求，约 63 秒落在未记录的发音查询/保存区间，后者需分阶段计时后才能确认。需要在后续实现中增加阶段耗时/进度日志、避免非关键发音查询拖慢主分析，并提供端到端超时/失败落盘保障。
- 决策：保留可恢复的 pending 状态，但需让失败原因和最后进展可见；分析流程需有明确超时/失败落盘保障，重试不得永久等待超时窗口。后续排查应对照 `logs` 中材料导入及 AI 调用日志和对应分析记录，区分外部请求耗时、进程中断及保存失败。
- 实施范围：Domain 检查状态语义是否足够表达超时；Service 增加可观测进展与可靠失败收敛；UI 展示错误和恢复操作，并说明处理中状态。

## 第 4 条：点击发音无声音并显示播放失败

- 调查结论：`components/learning/TaskCard.tsx` 使用材料分析保存的 `pronunciationAudioUrl` 调用浏览器 `audio.play()`；拒绝或媒体错误时显示“播放失败”。当前记录引用的 `image-13.png` 未随文件提交，无法仅凭记录判断音频 URL 或设备原因。需检查失败 URL、HTTP 响应、浏览器播放策略和媒体格式支持。
- 决策：明确区分无音频、正在播放与播放失败；播放失败时提供可诊断的来源/重试信息。词典音频不可用不得导致材料分析失败。
- 实施范围：Domain 不涉及；Service 核查音频地址的来源与有效性，失败不阻断分析；UI 保留状态提示并提供有用的恢复/来源信息。
